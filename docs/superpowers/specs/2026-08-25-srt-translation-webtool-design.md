# SRT 中翻英網頁工具 — 設計規格書

日期：2026-08-25

## 背景與目的

同事需要一個網頁工具：上傳已完成 Stage 2/3（糾錯、格式化）的中文 SRT 字幕檔，
自動產出符合 `tzu-chi-srt-pipeline` skill Stage 4 規則的英文 SRT 字幕檔，
翻譯時套用 Drust 資料庫中的 `translation_glossary`（鎖定詞彙庫）以確保用詞一致。

## 範圍（MVP）

**包含：**
- 上傳中文 `.srt` → 產出英文 `.srt`（Stage 4 翻譯，1:1 逐行對應）
- 套用 `translation_glossary` 鎖定詞彙
- 不確定/新詞彙寫入 `pending_terms`（狀態 `pending`，供事後人工確認）
- 本機執行，之後由使用者自行以 Cloudflare Tunnel 對外開放

**不包含（明確排除）：**
- Stage 1 轉錄、Stage 2 語音糾錯、Stage 3 格式化 —— 假設輸入的中文 SRT 已完成
- 詞彙庫的線上編輯介面（`pending_terms` 確認流程仍在既有的人工/Claude Code 對話中進行）
- 使用者帳號/權限系統（MVP 為單一內部工具，暫不做登入）

## 架構總覽

不使用 Claude Artifact（其嚴格 CSP 不允許呼叫任意自架後端）。改用**本機 Flask
應用**，同一個 origin 同時提供前端頁面與 API，未來以 `cloudflared tunnel`
直接對外開放同一個 port，不會有跨網域問題。

```
瀏覽器（同事）
   │  上傳中文 .srt
   ▼
Flask 網站（本機執行，之後 Cloudflare Tunnel 對外）
   ├─ 靜態頁面：上傳 / 進度 / 下載 / 待確認詞彙清單
   └─ POST /translate
        1. 解析 SRT → cue 陣列（序號、時間碼、文字）
        2. 向 Drust REST API 讀取 translation_glossary（anon token）
        3. 依 40–60 條切批，逐批呼叫本機 `claude -p`（headless）
        4. 每批驗證：條數/編號/時間碼與原文一致 → 不符則重試（上限 N 次）
        5. 組合全部批次 → 用鎖定詞彙庫做字串一致性校正
        6. 不確定詞彙 → 寫入 Drust pending_terms（service token，僅後端使用）
        7. 回傳：翻譯後 SRT 文字 + 警告清單 + 本次新增的待確認詞彙清單
   ▼
瀏覽器下載 [英文字幕]<標題>.srt
```

## 元件細節

### 1. Drust 連線
- Host: `https://tcdrust.tzuchi-org.tw`
- REST base: `/t/9eec6c81-f435-4811-b86d-a4829edbecea/`
- 讀取 `translation_glossary`：使用 anon token（唯讀，安全，可寫在後端設定檔）
- 寫入 `pending_terms`：使用 service token（**只存在後端環境變數/設定檔，絕不傳到瀏覽器**）
- Drust 連不上時：直接中止整個翻譯請求並回傳明確錯誤，不在缺詞彙庫狀態下硬翻（犧牲精準度不可接受）

### 2. 翻譯引擎（本機 Claude Code CLI，headless）
- 呼叫方式：`claude -p "<prompt>" --dangerously-skip-permissions`（非互動、無需人工按確認鍵；因為只在本機受信任環境執行，且 prompt 內容完全由後端組裝、不含使用者可注入的任意指令）
- 每批 prompt 內容：
  - Stage 4 規則摘要（1:1 逐行、海外志工姓名用漢語拼音、經典書名意譯等，見 SKILL.md）
  - 相關詞彙庫條目（可先用簡單字串比對，只夾帶批次內文字有出現到的詞彙，避免 prompt 過長）
  - 前一批最後 2–3 條的中英對照，作為語境銜接
  - 本批次的中文 cue 列表（含序號）
  - 明確要求：輸出必須是「序號 + 英文譯文」的結構化格式，且序號需與輸入完全一致；不確定的詞彙需用固定標記包住（例如 `[[UNSURE:詞彙|備選翻譯]]`）方便後端解析

### 3. 批次驗證與重試
- 每批驗證項目：回傳條數 == 輸入條數、序號集合相同、（時間碼不經過模型，直接沿用原始輸入，模型只負責文字）
- 驗證失敗 → 重試同一批（換句話說明確要求修正），最多 3 次
- 3 次仍失敗 → 該批 cue 文字改為 `[翻譯失敗-請人工確認]`，時間碼/序號照舊保留，繼續處理下一批，最終在回傳的警告清單中列出失敗批次範圍

### 4. 詞彙一致性校正（純字串比對，不呼叫模型）
- 掃描每個中文 cue，若包含 `translation_glossary` 中 `locked=1` 的中文詞彙，檢查對應英文 cue 是否包含該鎖定英文譯法
- 不一致 → 直接用鎖定譯法覆蓋校正，並記錄一筆校正日誌（顯示在警告清單，方便使用者知道模型原本翻得不一致）

### 5. 待確認詞彙處理
- 解析每批輸出中的 `[[UNSURE:...]]` 標記 → 整理成清單
- 逐筆 `insert_record` 到 `pending_terms`（`stage: translation`, `status: pending`, `context`, `suggested_fix`, `video_title` 取自檔名）
- 同一詞彙同次翻譯只寫入一次（去重）
- 回傳給前端顯示，讓同事知道這次翻譯有哪些詞彙還沒鎖定

### 6. 前端頁面
- 單頁：檔案上傳（限 `.srt`）、「開始翻譯」按鈕
- 翻譯中：顯示批次進度（第 X / 共 Y 批）
- 完成後：
  - 下載按鈕（檔名沿用 `[英文字幕]<原標題>.srt` 慣例）
  - 警告清單（失敗批次、詞彙校正紀錄）
  - 本次新增待確認詞彙清單（供同事口頭/事後跟您確認）

## 錯誤處理總表

| 情境 | 處理方式 |
|---|---|
| 上傳檔案非合法 SRT 格式 | 拒絕，回傳明確錯誤訊息 |
| Drust 讀取詞彙庫失敗 | 中止整個請求，提示「無法連線詞彙庫」 |
| `claude` CLI 呼叫失敗/逾時 | 該批次視為失敗，走批次重試/失敗標記流程 |
| 批次驗證失敗（條數/序號不符） | 自動重試最多 3 次，仍失敗則標記該批並繼續其他批次 |
| Drust 寫入 pending_terms 失敗 | 不中止翻譯結果回傳，但在警告清單中提示「部分待確認詞彙未成功記錄」 |

## 測試計畫

1. SRT 解析/重組單元測試：解析後再序列化應與原始結構等價
2. 批次切分單元測試：條數邊界、序號連續性
3. 批次驗證邏輯單元測試：條數/序號比對、觸發重試的情境
4. 整合測試：取資料夾內既有中文 SRT 的一小段（20–30 條）跑完整流程，人工檢視翻譯品質與詞彙庫套用是否正確
5. 手動瀏覽器測試：上傳 → 進度顯示 → 下載 → 檔案內容檢查
